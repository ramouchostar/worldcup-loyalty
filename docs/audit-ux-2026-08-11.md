# Audit UX/UI — interface membre vs guidelines « faible littératie numérique »

**Date : 11 août 2026.** Audit de l'interface actuelle contre le référentiel `docs/ux-guidelines-saas-non-tech.md`, mené par 5 passes parallèles avec lecture intégrale du code : **boutons et cibles tactiles** (~97 éléments interactifs, 27 fichiers), **menus et navigation**, **formulaires et authentification**, **textes / états vides / progression**, **accessibilité technique**. Chaque constat est ancré `fichier:ligne`.

## Verdict global

L'app est **nettement au-dessus de la moyenne** pour ce public et porte les traces d'audits antérieurs sérieux : zoom jamais bloqué, BottomNav exemplaire (5 onglets icône + libellé, Scanner au centre), conformité **ADR 0007 totale** (zéro euro sur les surfaces membres, vérification exhaustive), timers tous réels (aucun dark pattern d'urgence), messages goal-gradient (« encore X avant [conséquence] ») déjà généralisés, états vides instructifs sur 9 surfaces sur 10, focus clavier jamais supprimé sans remplacement, consentements RGPD propres.

Les problèmes se concentrent sur **7 chantiers transverses** — dont 5 sont des quick wins :

| # | Constat consolidé | Gravité | Effort |
|---|---|---|---|
| 1 | L'authentification est 100 % mot de passe — le magic link annoncé par CLAUDE.md n'existe pas dans le code | 🔴 Critique | Gros |
| 2 | Aucun point d'aide / contact humain sur aucun écran (WCAG 3.2.6) | 🔴 Critique | Quick win |
| 3 | Modales PWA + push bloquantes dès la première visite, avant toute valeur | 🔴 Critique | Faible |
| 4 | Les boutons transactionnels clés font ~28 px de haut (gabarit `text-xs py-1.5`) | 🔴 Critique | Quick win |
| 5 | Vocabulaire incohérent et trompeur : « Commander → » qui scanne, « Soumettre » ×7, « cadeaux » vs « récompenses », « Déco » | 🟠 Majeur | Quick win |
| 6 | Erreurs Supabase affichées en anglais brut ; erreurs jamais rattachées au champ fautif | 🟠 Majeur | Faible |
| 7 | Aucune progression dotée : toutes les barres démarrent à 0 % ; succès silencieux après « Mettre de côté »/« Échanger » ; écran de succès sans les 3 lignes gagnées | 🟠 Majeur | Faible→Moyen |

Bilan chiffré cumulé (après dédoublonnage inter-rapports) : **~10 constats critiques, ~35 majeurs, ~40 mineurs — et ~60 points déjà conformes à préserver.** Environ 70 % des corrections sont des quick wins de libellés ou de classes Tailwind.

## 1. Constats critiques (détail)

### C1 — Pas de magic link : auth 100 % mot de passe, 10 champs à l'inscription
Confirmé par 3 passes indépendantes. `app/(auth)/login/actions.ts:36` (`signInWithPassword`), `app/(auth)/signup/page.tsx:51`, existence de `forgot-password`/`reset-password`. Aucun `signInWithOtp` dans le code — alors que CLAUDE.md annonce « magic link + Google OAuth » et que `app/auth/callback/route.ts:40` sait déjà traiter `verifyOtp`.

Aggravations en chaîne :
- **`/signup` = 10 champs sur un écran** (prénom, nom, email, téléphone, date de naissance, 3 zones, mot de passe ×2) — ~2× le maximum ; à −5–10 % de conversion par champ, c'est le formulaire le plus coûteux du produit (`signup/page.tsx:9-20, 115-258`).
- **Re-saisie interdite** : signup collecte date de naissance + zones, puis `/register` les **redemande dans des champs vides** (`register/page.tsx:76-97`) — violation WCAG 2.2 · 3.3.7 « Dites-le-nous une fois ».
- **Google relégué sous le formulaire** derrière « ou continuer avec » (`LoginForm.tsx:76-147`) — l'inverse de l'ordre recommandé pour ce public.
- Mot de passe = test de mémoire, violation WCAG 2.2 · 3.3.8 (Accessible Authentication).

**Plan** : (a) quick win — Google en premier sur login/signup, pré-remplir `/register` depuis les métadonnées signup ; (b) court terme — réduire `/signup` à l'essentiel et router vers `/register` comme le flux OAuth (le backend existe déjà) ; (c) structurel — `signInWithOtp` magic link + repli OTP 6 chiffres, consigne « Ouvre l'email sur CE téléphone », bouton « Renvoyer l'email » (chiffre de réf. : Calendly 43 % → 71 % de complétion).

### C2 — Aucun point d'aide ni de contact humain (WCAG 2.2 · 3.2.6)
Aucun lien d'aide dans le header (`app/r/[restaurantId]/layout.tsx:73-90`), la BottomNav, ou `/compte`. Preuve aggravante : `micro-rewards/page.tsx:220` affiche « Rejetée — contacte-nous pour plus d'informations » **sans aucun canal de contact nulle part dans l'app**. Un ticket rejeté est le moment d'anxiété maximale ; 40 % du public cible abandonne sans filet humain.

**Plan (quick win)** : lien « Aide » permanent et identique sur chaque écran (header membre), pointant vers un `wa.me/<numéro du resto>` pré-rempli + mini-page « Besoin d'aide ? » rappelant que le comptoir peut agir pour le client. Remplacer le « contacte-nous » mort par ce lien.

### C3 — Modales PWA + push bloquantes à la première visite
`components/member/OnboardingFlow.tsx:73-85` : `computeStage()` retourne `"pwa"` dès la première visite du dashboard (aucune condition de moment de valeur), enchaîne la modale push (295-331), puis le tour **forcé** (`allowClose: false`, l.125-126, sans bouton Passer). Trois interruptions séquentielles avant d'avoir rien scanné ni rien gagné — l'anti-pattern « murs de prompts à la première visite » du référentiel (les prompts différés font jusqu'à 6× plus d'installations).

**Plan (faible)** : conditionner `computeStage()` à ≥ 1 commande validée (donnée déjà chargée par le dashboard, à passer en prop) ; push après la première récompense ; `allowClose: true` + bouton Passer sur le tour. Les modales elles-mêmes sont bien faites (pré-prompt custom, fiche iOS illustrée, boutons de refus présents — à préserver).

### C4 — Boutons transactionnels ~28 px de haut
Le gabarit `text-xs px-3 py-1.5 rounded-full` (~28 px, sous le plancher où les erreurs de tap triplent) sert les actions les plus importantes du produit :
- `my-rewards/RedeemButton.tsx:36` — « 🎁 Récupérer », l'action la plus corrélée au surcroît de dépense (+25 % McKinsey)
- `my-rewards/BankButton.tsx:42-73` — « Mettre de côté » + confirmation « Oui »/« Non » (~28 px, espacées de 6 px < 8 px, « Non » en ghost) sur une action **irréversible**
- `reserve/ExchangeButton.tsx:39-45` — « Échanger » (débite la réserve)
- `TeamManager.tsx:187-193` — « Rejoindre » une équipe (action clé de l'onboarding ADR 0018)
- `app/join/page.tsx:96-103` — « Rejoindre » (~32 px), **sans état pending** (`useFormStatus` absent : aucun feedback au tap, double soumission possible ; idem formulaires de la landing `r/[restaurantId]/page.tsx:123-263`)
- `dashboard/page.tsx:252-257` — CTA hero (~28 px, en haut d'écran hors zone du pouce)
- `components/member/UserNav.tsx:38-54` — header : 3–4 cibles de ~26 px espacées de < 8 px

**Plan (quick win, ~1 jour)** : un composant/classe `btn` unique (`min-h-[48px] px-5 text-sm font-semibold rounded-xl` fond plein) appliqué à ces 10 emplacements + `useFormStatus` sur les server actions de `/join` et de la landing. Corrige d'un coup les 6 critiques boutons et la moitié des majeurs.

### Erreurs de formulaire
- **Erreurs Supabase brutes en anglais** montrées au membre : `signup/page.tsx:66`, `forgot-password:24`, `reset-password:33` (« User already registered »…). Mapper 4–5 codes vers du français orienté solution. *(Faible)*
- **Erreurs en bloc global, jamais à côté du champ** (tous formulaires : `LoginForm:106`, `signup:260`, `register:129`, `TeamManager:157`…) — pas de bordure rouge, pas d'icône, pas d'`aria-describedby`. Composant `FieldError` à créer. *(Moyen)*
- **Aucune validation au blur** (le +22 % réussite / −42 % temps du référentiel) ; au moins la validation à la frappe est évitée. *(Moyen)*
- **`autocomplete` absent sur signup/reset** (`given-name`, `email`, `new-password`…) — l'auto-remplissage, béquille essentielle de ce public, échoue. Le login est conforme, lui. *(Trivial)*
- Échec silencieux de la réponse au fil feedback (`FeedbackClient.tsx:235-255`) ; code d'invitation invalide → redirection muette (`join-team/route.ts:23-25`, cookie 15 min trop court) ; permission push refusée → bannière qui revient sans explication (`PushNotificationBanner:34-38`).

### Progression et feedback
- **Aucune progression dotée** : jetons 0/4 (`micro-rewards:104-112`), parrainage 0/5 (`:305-313`), `TokenProgressRing` gris à 0, « 0 % » écrit en toutes lettres (`rewards:207`), « 0 » nu sur la réserve (`reserve:69`). Levier mesuré ×1,8 (34 % vs 19 %). Plan : **jeton de bienvenue à l'inscription** (décision produit, coût plafonné ADR 0017) ou a minima plancher visuel `max(pct, 6 %)` + suppression du « 0 % » + première cible affichée sous le solde réserve. *(Faible→décision produit)*
- **« Mettre de côté » et « Échanger » redirigent sans aucun message de succès** (`BankButton.tsx:26-28`, `ExchangeButton.tsx:23-26`) — ajouter un bandeau « ✅ +120 dans ta réserve » / « 🎉 {cadeau} ajouté — récupère-le sous 48 h ». *(Faible)*
- **L'écran de succès du scan ne récapitule pas les 3 lignes gagnées** (`submit-order:188-218`) — afficher les 3 items de la `pending_reward` créée (ADR 0006/0010, en points, ADR 0007). *(Moyen — l'API doit renvoyer le détail au 201)*
- **Empty state leaderboard muet** (`LeaderboardRealtime.tsx:50-52`) — le seul trou : « Crée la première équipe et prends la tête du classement ! » + CTA. *(Trivial)*

### Accessibilité
- **Contraste du timer coupon : `text-amber-500` = 2,15:1** entre 5 et 2 minutes restantes (`CouponClient.tsx:53`) — sur l'écran le plus critique du parcours, utilisé au comptoir, parfois en plein soleil. → `text-amber-700`. Token en `text-gray-300` = 1,47:1 (`:157`) → `text-gray-600`. Instruction « Montre cette page au comptoir » en `text-xs gray-400` (`:177-179`) → `text-sm gray-600`. *(Trivial, à faire en premier)*
- **Systémique : 105 × `text-gray-400` (2,54:1) et 171 × `text-xs` (12 px)** sur les surfaces membres, y compris du contenu porteur (étiquettes de couche, échéance 48 h, seuils, libellés BottomNav à 12 px). Règle : `text-gray-500` minimum quand le texte informe, `text-xs` réservé aux métadonnées, nav à 14 px. *(Moyen, mécanique)*
- **`text-brand-gold` sur fond clair = 2,10:1** (`dashboard:265-268`, `TeamManager:204`) — la couleur est pilotée par établissement (m37/m48) : prévoir un **garde-fou de contraste dans `lib/branding.ts`**. *(Moyen)*
- **~15 champs sans `htmlFor`/`id`** (submit-order, login, signup, register, TeamManager) et **placeholder-comme-label** sur TeamManager (code, nom, zone), textareas feedback, email parent. *(Faible, mécanique)*
- **Aucun `prefers-reduced-motion`** côté membre (spinners, pulses, barre du coupon animée 10 min) — un bloc global dans `globals.css` couvre tout. *(Faible)*
- **Boutons retour incohérents** : flèche seule sans aria-label ni padding (`my-rewards:40`, `reserve:57`), avec aria-label ailleurs, texte ailleurs, absents ailleurs — un composant `BackLink` unique « ← Accueil » ≥ 44 px. *(Quick win)*
- Modales onboarding sans `role="dialog"`/`aria-modal`/piège de focus ; bug pastille active BottomNav (`absolute bottom-0` sans `relative` sur le Link, `BottomNav.tsx:34-53`) ; suppression de compte via `window.confirm` natif (`AccountActions.tsx:14-17`).

### Navigation (au-delà de C2)
- **RestaurantSwitcher affiché avec chevron en mono-restaurant** (`RestaurantSwitcher.tsx:20-61`) — affordance parasite pour le cas ultra-majoritaire ; rendre un `<span>` statique si ≤ 1 resto. *(Quick win)*
- **/compte hors layout membre** : perd header + BottomNav, retour vers un resto arbitraire (`limit(1)`) — déplacer sous `/r/[restaurantId]/compte` ou passer `?from=`. *(Moyen)*
- **Tuiles dashboard sans affordance tactile** (hover invisible au doigt) — ajouter « → ». Tuile réserve « Échange-la contre un gros cadeau » affichée à solde 0 (`dashboard:490`). *(Trivial)*
- **Admin mobile : hamburger 16 entrées** (`AdminMobileNav.tsx`) — compromis assumé ADR 0030 §9, mais une bottom nav 4 entrées « Au quotidien » + « Plus » servirait mieux un restaurateur entre deux services. Détection de page active par égalité stricte (`pathname ===`) : rien de surligné sur les sous-pages. *(Moyen)*
- `/login` sans issue vers le site public en PWA standalone. *(Trivial)*

### Performance vieux appareils
- **9 familles Google Fonts chargées dans le layout racine** (`app/layout.tsx:11-31`) pour tous les membres, y compris les polices réservées à l'admin et à la landing B2B — 46–53 % des seniors ont un téléphone > 2 ans. Déplacer vers les layouts concernés (attention au mécanisme `--brand-font`). *(Moyen)*
- Image hero du dashboard injectée en `background-image` sans redimensionnement (`dashboard:198-205`) : une photo 4 Mo uploadée par le restaurateur arrive telle quelle → transformation Supabase `?width=800`. *(Faible)*

### Dette de code
- `components/member/RewardProgressBar.tsx` : **mort** (aucun usage), lit l'ancienne table `rewards`.
- `components/InstallBanner.tsx` + `components/PushNotificationBanner.tsx` : **jamais importés**, supplantés par OnboardingFlow, avec deux jeux de clés localStorage concurrents. À supprimer pour éviter la résurrection de libellés non audités.
- `ActionCardsSection.tsx:98-109` : « J'ai suivi » ouvre le lien **et** soumet la claim dans le même geste (biais déclaratif).

## 3. Points conformes — à préserver (ne pas « réparer »)

1. **BottomNav** : 5 onglets max (décision commentée), icône + libellé texte, `aria-current`, cibles ~52 px, `pb-safe`, Scanner au centre — applique les quick wins 6 et 9 à la lettre.
2. **ADR 0007/0028 : conformité totale** — points partout, € uniquement à la saisie du ticket, types défensifs (`Omit<…, "total_spent">`), colonnes de coût jamais sélectionnées, messages de verrou neutres.
3. **Zoom jamais bloqué** (commentaire de non-régression dans `app/layout.tsx:85-95`) ; focus jamais supprimé sans `focus:ring-2` de remplacement (38/38).
4. **Timers tous réels** (coupon 10 min, 48 h, appliqués serveur) — zéro compte à rebours décoratif, zéro case pré-cochée, opt-out en un tap : aucun dark pattern.
5. **Goal gradient généralisé** : « encore X avant [conséquence concrète] » sur 6 surfaces — le point fort de l'app.
6. **Fallback ADR 0010** (« prévisualiser pour €25 ») implémenté et invisible en euros ; états vides instructifs sur 9 surfaces sur 10.
7. **Parcours submit-order largement exemplaire** : grande zone d'upload avec équivalent clic, caméra ET galerie, `inputMode="decimal"`, bouton final `py-4` avec disabled expliqué, anti-double-tap, « Vérification en cours… » conforme ADR 0008, garde anti-blocage réseau, double chemin de reprise OCR (saisie manuelle OU vérification sous 2 h), écrans de succès orientés « Voir mes cadeaux → ».
8. **Culs-de-sac systématiquement bouchés** (audits antérieurs) : /compte, /register, leaderboard anonyme, /join avec bannières de refus, coupon.
9. **Boutons WhatsApp** (partage équipe, parrainage) : premier canal, message pré-rempli court — quick win 11 déjà appliqué.
10. **FeedbackClient** : grandes cartes de choix fermées, meilleur pattern « disabled expliqué » du produit, saisie conservée en cas d'échec.
11. **Profondeur de navigation remarquable** : scanner = 1 tap, cadeaux = 1 tap, coupon = 1–2 taps.
12. **Erreurs API en français simple** avec cause + action sur les chemins principaux ; statuts jamais signalés par la couleur seule ; `sr-only` sur TokenProgressRing ; instructions iOS illustrées.

## 4. Plan d'action priorisé

**Sprint 1 — quick wins (~2–3 jours, ~80 % des critiques réglés)**
1. Contrastes du coupon (`amber-700`, `gray-600`) — 30 min, écran le plus critique.
2. Composant `btn` ≥ 48 px appliqué aux 10 boutons transactionnels + `useFormStatus` sur /join et la landing.
3. Passe de libellés (tableau §2) : Commander→Scanner, Soumettre→Envoyer, cadeaux/récompenses, Déco, cashier, solo, Continuer ×4.
4. Lien « Aide » permanent → WhatsApp du resto + mini-page (règle C2).
5. Différer les modales PWA/push après le 1er ticket validé ; tour passable (`allowClose: true`).
6. Erreurs Supabase → français ; `autocomplete` sur signup/reset ; bouton « Renvoyer l'email » + consigne d'appareil.
7. Bandeaux de succès bank/exchange ; empty state leaderboard ; plancher visuel des barres + suppression du « 0 % ».
8. `prefers-reduced-motion` global ; `htmlFor`/`id` sur les 15 champs ; labels visibles sur TeamManager/feedback ; composant `BackLink` ; bug pastille BottomNav ; suppression des 3 fichiers morts.

**Sprint 2 — moyen (~1 semaine)**
9. Google en premier + pré-remplissage `/register` + réduction de `/signup` (aligné flux OAuth).
10. Écran de succès avec les 3 lignes gagnées (API à enrichir au 201).
11. Passe systémique `text-gray-400`→`gray-500+` et `text-xs`→`text-sm` sur contenu porteur ; garde-fou contraste dans `lib/branding.ts`.
12. Erreurs par champ (`FieldError` + blur) ; `/compte` sous le layout membre ; polices par layout ; image hero redimensionnée.

**Structurel (à planifier)**
13. Magic link + OTP (règle WCAG 3.3.8 à la racine, rend forgot/reset obsolètes).
14. Jeton de bienvenue (progression dotée — décision produit, plafond ADR 0017).
15. Bottom nav admin mobile 4 entrées + « Plus ».
16. Tests utilisateurs en restaurant avec de vrais clients seniors (la pratique la plus étayée du référentiel) ; instrumentation du funnel d'activation (temps-vers-valeur, taux de récupération).
